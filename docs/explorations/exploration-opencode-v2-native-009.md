# Exploration: Native OpenCode V2 integration for ArggonManager (opencode-v2-native-009)

Spike record: compare the candidates below, cite dated sources, and record a
recommendation. The decision itself lands in an ADR (`docs/adr/`) — link it
under Decision. A technology playbook (`arggon playbook new`) is generated
after the decision.

Sources are the OpenCode **V2** documentation only (https://opencode.ai/v2/docs/,
accessed 2026-09-17) plus local checks on `opencode v2.0.7` (2026-09-17). No V2
runtime behavior was exercised beyond `--version`; every claim below is
documentation-sourced unless marked as local evidence. V1 documentation was not
used.

## Candidates

- **A — Status quo.** Keep the current wiring: generated `AGENTS.md`, bundled
  `.agents/skills/arggon-cli` (+ `arggon-upgrade`), project-scoped `.mcp.json`,
  and the `arggon mcp` stdio server. No OpenCode-specific artifacts.
- **B — Declarative `.opencode/` artifacts generated by `arggon init`.**
  OpenCode V2 project config (`mcp.servers.arggon`, optional formatter and
  compaction defaults), agent definitions (coordinator / worker / reviewer) and
  commands (`/arggon-next`, `/arggon-claim`, `/arggon-done`, `/arggon-handoff`)
  as files, using the existing never-overwrite + `x-generated` provenance
  machinery.
- **C — Behavioral OpenCode V2 plugin** (published package or vendored
  `.opencode/plugins/arggon/`). A thin V2 plugin that (1) registers the arggon
  MCP server when absent, (2) injects bounded "current work item" context per
  session (branch → item via `arggon show --json`), (3) re-injects it around
  compaction, (4) optionally surfaces tracker status natively.
- **D — Reverse embedding via `@opencode/sdk` inside the CLI.** Host OpenCode
  from an `arggon` command to run delegated work (e.g. execute the adopt
  checklist) without the user's TUI.

## Criteria

Non-negotiables (from [docs/engineering.md](../engineering.md) and
[docs/agents.md](../agents.md)):

1. The git-native tracker (`tasks/`) stays the single source of truth; no
   parallel schema and no agent-only dialect of the rules.
2. Rule enforcement stays in `cli/src/rules.ts` (one module, CLI + MCP parity).
   The integration may surface rules, never fork them.
3. The CLI and MCP surfaces keep working for non-OpenCode agents (Claude Code,
   Codex, CI): **no hard dependency on OpenCode**.
4. Minimal dependency surface; a new runtime dependency needs justification.
5. Generated files: never-overwrite + provenance; adopters own their config.

Weighted criteria: token/context efficiency (ADR 0006), adoption cost,
maintenance risk against a young V2 API (2.0.x), upgrade path with version
pinning, reviewer visibility.

## Findings

### Already working implicitly (no new code)

- **`AGENTS.md`**: `arggon init` generates the repo `AGENTS.md`; V2 loads the
  global `AGENTS.md` plus every `AGENTS.md` from the workspace directory toward
  home, nearest last, and combines them (source:
  https://opencode.ai/v2/docs/instructions/, 2026-09-17). V2 recognizes
  `AGENTS.md` only and does **not** use `CLAUDE.md` as a fallback — the
  generated `CLAUDE.md` shim serves other tools, not V2.
- **Skills**: `.agents/skills` is a documented project compatibility source;
  discovery order is `.claude/skills` → `.agents/skills` → `~/.config/opencode/
  skills` → project `.opencode/skills` → explicit `skills` config entries, later
  sources overriding by ID (source: https://opencode.ai/v2/docs/skills/,
  2026-09-17). Because init bundles `arggon-cli` and `arggon-upgrade` under
  `.agents/skills/`, **any V2 session in an initialized repo already discovers
  the skill today** — this is the most valuable implicit integration. Slash
  visibility is controlled by `slash` / `metadata.opencode/slash`;
  `metadata.opencode/autoinvoke: false` hides from the model list while keeping
  explicit loading.
- **MCP**: `arggon mcp` works over stdio with any MCP client. **Gap**: V2
  configures servers under `mcp.servers` in `opencode.json(c)` and uses
  `disabled` (not `enabled`); server names do not sit directly under `mcp`
  (source: https://opencode.ai/v2/docs/mcp-servers/, 2026-09-17). The V2 docs do
  not mention `.mcp.json`, so the `.mcp.json` that init generates today is
  **unverified for V2**; a native registration path is needed.
- **Commands/skills in ACP clients**: `opencode acp` advertises slash commands
  and skills to ACP clients (Zed et al.) and loads the working directory's
  config (source: https://opencode.ai/v2/docs/cli/acp/, 2026-09-17) — the
  implicit wiring travels automatically.

### Declarative artifacts (candidate B)

- **Config precedence**: every discovered `.opencode` config overrides every
  discovered direct config, at every level; settings merge, and files are
  merged from the farthest ancestor to the current directory (source:
  https://opencode.ai/v2/docs/config/, 2026-09-17). Generated-config
  consequence: writing `.opencode/opencode.json` would **override** an
  adopter's root `opencode.json`, so the respectful contract is to generate a
  config only when the adopter has none (root `opencode.json(c)` or
  `.opencode/opencode.json(c)`), and otherwise report the exact stanza in
  `doctor` instead of writing.
- **MCP override semantics**: a higher-precedence project config replaces the
  entire server object with the same name; otherwise every required field must
  be repeated (source: https://opencode.ai/v2/docs/mcp-servers/, 2026-09-17).
  Relevant to doctor guidance and to plugin auto-registration.
- **Agents**: `.opencode/agents/*.md`, with `mode` (`primary` / `subagent` /
  `all`), ordered `permissions` rules (last match wins; `allow` / `ask` /
  `deny`), `steps`, `hidden`, `model` (+`#variant`) (source:
  https://opencode.ai/v2/docs/agents/, 2026-09-17). The playbook's
  coordinator → subagent orchestration maps directly; subagent nesting depth is
  one by default, matching the current model (source:
  https://opencode.ai/v2/docs/tools/, 2026-09-17). `request` overlays are
  preserved but **not sent** in the current V2 runner — do not rely on them.
- **Commands**: `.opencode/commands/*.md` prompt templates with `$ARGUMENTS`,
  `$1..$n`, `agent`/`model`/`subagent` frontmatter; project files replace
  same-named global commands; only `.md` is discovered (source:
  https://opencode.ai/v2/docs/commands/, 2026-09-17). Shell blocks (`` !`cmd` ``)
  run when the command is evaluated, **outside the agent's tool permission
  flow**, and argument placeholders are expanded before execution — never place
  untrusted arguments in shell blocks (same source).
- **Subagent permissions**: `{action: "subagent", resource: "<agent-id>"}` is
  the documented gate for launching children (source:
  https://opencode.ai/v2/docs/agents/, 2026-09-17); the reviewer agent shape
  (deny edits, allow reads) is documented verbatim, so a review subagent can be
  generated with the repo's own review bar encoded as permissions.

### Behavioral plugin (candidate C)

- **Zero-config loading**: OpenCode loads direct `.ts`/`.js` files and
  immediate package directories from every discovered `.opencode/plugins/`
  directory, global or project, without a `plugins` config entry (sources:
  https://opencode.ai/v2/docs/plugins/ and
  https://opencode.ai/v2/docs/build/plugins/, 2026-09-17). A vendored plugin
  template therefore needs no adopter config — but package plugins can be
  versioned and upgraded via `opencode plugin add|update` (same sources).
- **Documented (non-experimental) surfaces**: `session.hook("prompt" |
  "context" | "compaction" | "title" | "generate")`, `tool.hook("execute.before"
  | "execute.after")`, `permission.hook("evaluate")`, `shell.hook(
  "create.before")`, transforms for `mcp`, `agent`, `command`, `skill`, `tool`,
  `reference`, `vcs`, `worktree`, `websearch`, `provider`, `model`,
  `integration`, plus `ctx.event.subscribe`, `ctx.storage`, `ctx.generate.text`,
  `ctx.session.*`, and plugin RPC (sources: https://opencode.ai/v2/docs/build/
  plugins/ and https://opencode.ai/v2/docs/build/plugins/rpc/, 2026-09-17).
  `experimental.ws.*` hooks are explicitly experimental and out of scope.
- **Highest-value behaviors for ArggonManager**:
  1. MCP auto-registration via `ctx.mcp.transform` only when
     `editor.get("arggon")` is absent — fixes the `.mcp.json` gap for every
     project that loads the plugin.
  2. Bounded current-item context: resolve the session's branch (or an explicit
     `ARGON_ITEM` env) to a work item and append an `arggon show <id> --json`
     summary via `session.hook("context")` — the same bounded surface ADR 0006
     already mandates.
  3. Compaction-safe re-injection: V2 compaction is checkpoint-based and
     lossy; re-injecting the item block after a checkpoint keeps long
     orchestration sessions anchored (sources:
     https://opencode.ai/v2/docs/compaction/ and the `compaction` hook above,
     2026-09-17).
  4. Optional tracker hygiene: on `tool.hook("execute.after")` for shell
     commands that commit, run `arggon validate --json` and surface failures —
     complements, never replaces, the pre-commit/CI gates.
- **Costs/risks**: V2 is at 2.0.x; the plugin API can drift (hooks are new),
  and plugin load failures are per-location. Mitigation: keep the plugin thin,
  version-pin `@opencode/plugin`, feature-detect, mark the plugin optional, and
  record a revisit trigger in the ADR.
- **TUI plugin**: CLI plugins use `@opencode/plugin/tui` with slots
  (`home.footer.status`, `sidebar.content`, `prompt.footer.status`), keymap
  commands, dialogs, toasts, routes, session panels (source:
  https://opencode.ai/v2/docs/build/plugins/cli/, 2026-09-17). Candidate for a
  later phase (status line + tracker panel); not first.

### Reverse embedding (candidate D)

- `@opencode/sdk` hosts OpenCode in-process (`OpenCode.create()`, sessions,
  worktrees, events, plugins) with no HTTP listener (source:
  https://opencode.ai/v2/docs/build/sdk/, 2026-09-17); a Cloudflare
  Durable-Object profile exists (source:
  https://opencode.ai/v2/docs/build/sdk/cloudflare/, 2026-09-17). This inverts
  the dependency (`arggon` → `@opencode/sdk`) and adds a new top-level package,
  which per [docs/engineering.md](../engineering.md) needs an ADR. Rejected as
  a first step under criterion 3; revisit only if delegated execution inside
  the CLI becomes a product requirement.

### Inert / unsupported V2 surfaces (do not build on)

| Surface | State |
| --- | --- |
| `instructions` config array | Accepted but entries are not loaded; `AGENTS.md` is the mechanism (https://opencode.ai/v2/docs/instructions/) |
| Agent `request` overlays | Preserved but not sent yet (https://opencode.ai/v2/docs/agents/) |
| Session sharing (`share`) | Not supported yet (https://opencode.ai/v2/docs/sharing/) |
| `username` | Accepted, not displayed (https://opencode.ai/v2/docs/config/) |
| Built-in `scout` agent | V2 has none (https://opencode.ai/v2/docs/agents/) |
| `warming` | Exists, disabled by default, real provider requests/cost; keep off for arggon work (https://opencode.ai/v2/docs/warming/) |
| `formatter` | Available and cheap: `formatter: true` runs project-local prettier after write/edit/patch (https://opencode.ai/v2/docs/formatters/) |
| Snapshots (`/undo`) | Active-directory files only inside a git worktree; no git state (commits/branches), no ignored files, untracked >2 MiB not captured; cannot revert tracker auto-commits (https://opencode.ai/v2/docs/snapshots/) |
| Compaction | Checkpoint-based, lossy; hooks can observe/override; tune `compaction.keep.tokens` per project (https://opencode.ai/v2/docs/compaction/) |
| MCP `_meta.sessionID` | Sent by OpenCode on calls made for a session; opaque correlation only, never auth (https://opencode.ai/v2/docs/mcp-servers/) |

### Local evidence (this repo, 2026-09-17)

- `opencode --version` → `v2.0.7`; the repo has **no** `.opencode/` and no
  `opencode.json(c)` (`check_index_coverage` scope `.opencode`: 0 entries;
  filesystem check: absent) — nothing to migrate.
- `arggon init` bundles both skills to `.agents/skills/` (`cli/src/docs.ts:162`)
  and generates `.mcp.json` from `templates/docs/mcp-json` (`cli/src/docs.ts:182`).
- The MCP surface is 9 tools, parity-tested against the CLI
  (`cli/src/mcp-parity.test.ts`), additive-only schema changes.
- `arggon instructions` extracts snippets from `docs/agents.md` by heading
  (`### Pre-commit gate`, `### CI gate`, `### Agent instructions snippet`,
  `cli/src/instructions.ts:53-55`) — a new OpenCode section is printable only if
  a matching extraction hook is added.

### Risk register (V2 churn)

| Risk | Mitigation |
| --- | --- |
| MCP registration shape changes | Plugin transform + doctor verification; keep `.mcp.json` for other clients |
| Plugin API drift (2.0.x) | Thin, optional, version-pinned plugin; ADR records revisit trigger |
| Two worktree conventions (`arggon start --worktree` → `../<repo>-<id>` vs OpenCode `worktree.directory`) | Keep arggon authoritative; document alignment guidance; no plugin worktree strategy in phase 1 |
| Inert features silently relied upon | The table above; no dependency on them |
| `.agents/skills` precedence below project `.opencode/skills` | Do not generate duplicate skill IDs under `.opencode/skills` |

## Recommendation

Adopt **B + C, staged, with A kept as the working baseline**:

1. **Phase 1 — declarative seam (B, no new runtime deps):** `arggon init`
   generates the OpenCode V2 seam — project config only when the adopter has
   none (never overwrite), agent definitions (coordinator / worker / reviewer)
   and commands as template files with `x-generated` provenance, drift tests,
   and JSON-validity checks like `.mcp.json`. `arggon doctor` gains an OpenCode
   section: V1-shaped config detection (top-level `mcp.<name>`, `enabled`,
   `autoupdate`), artifact presence, and native-registration status.
2. **Phase 2 — behavioral plugin (C, behind an ADR):** thin, version-pinned
   plugin for MCP auto-registration, bounded current-item context injection,
   and compaction-safe re-injection. Published package vs vendored template is
   the ADR's decision.
3. **Phase 3 — optional:** TUI plugin (status line + tracker panel + slash
   commands) and, only if the product demands it, SDK embedding as a separate
   ADR (D).
4. **Cross-cutting, any phase:** MCP `_meta.sessionID` attribution for
   `comment`/`handoff` defaults; technology playbook `docs/playbooks/opencode.md`
   pinned to 2.0.7; docs updates (`docs/agents.md` §Reference integrations,
   README, `docs/json-output.md` if the MCP surface changes).

Why B+C: B delivers the functionality with zero new runtime dependencies and
full reviewer visibility (files in git, diffable, never-overwrite machinery
already exists); C adds only the behaviors files cannot express and stays
optional. A alone leaves the concrete `.mcp.json` gap open; D is
disproportionate as a first step.

Out of scope (anti-goals): duplicating the rule engine in the plugin, moving
decision logic out of `cli/src/rules.ts`, making the core CLI depend on
OpenCode, and inventing a separate OpenCode-only workflow dialect.
