# 0007 MCP specification 2026-07-28: partial adoption for the stdio server

- Status: Proposed
- Date: 2026-09-15
- Deciders: Lead Architect (coordinator, accepts at merge), Arggon (author)
- Research: [exploration-mcp-2026-07-28-004](../explorations/exploration-mcp-2026-07-28-004.md) (task-mcp-spec-2026-eval)

## Context

The MCP 2026-07-28 specification (published 2026-09 timeframe, sources
accessed 2026-09-15) is the largest protocol revision to date: a stateless
core (handshake and `Mcp-Session-Id` removed; per-request capability
negotiation), an Extensions framework (Tasks, MCP Apps, Skills over MCP),
multi round-trip requests replacing stream-dependent elicitations, cacheable
list endpoints (`ttlMs`/`cacheScope`, deterministic catalog ordering), and
tightened HTTP authorization (CIMD, DCR deprecation, RFC 8707 audience
binding). Roots, Sampling, Logging, and the legacy HTTP+SSE transport are
deprecated. Updated TypeScript/Python/Go/C# SDKs shipped with the spec; the
TypeScript SDK gained `createMcpHandler` on Web Standards. The new core is
HTTP-oriented; stdio remains a valid transport for local applications but
gets no new features.

ArggonManager's server (`cli/src/mcp-server.ts`) is a hand-rolled,
dependency-free stdio JSON-RPC implementation: `initialize` handshake
negotiating 2024-11-05/2025-03-26/2025-06-18, a static deterministic
`tools/list`, and 9 synchronous tools that re-read `tasks/` from disk per
call against a fixed repo root. No session state, no caches, no HTTP
surface, no auth, no long-running operations.

Constraints: current MCP hosts on stdio negotiate older protocol versions
and expect the handshake; the server's envelope contract (`--json`
envelopes as tool text) is covered by tests and documented; we maintain one
transport and nine fast tools — an SDK dependency buys little.

## Decision

**Partial adopt.** Per capability:

| Capability | Decision | Rationale |
| --- | --- | --- |
| Stateless core | **ADOPT (declared compatibility)** | Our execution model is already request-scoped (per-call loads, no session state), so we are semantically stateless. Keep the stdio handshake and add `2026-07-28` to `SUPPORTED_PROTOCOL_VERSIONS` so newer clients negotiate up while existing clients keep working. No wire-format rewrite: the stateless core's drivers (sticky sessions, replay, horizontal scaling) do not exist on a local stdio pipe. |
| Tasks | **DEFER** | All 9 tools complete synchronously in milliseconds; the slowest (`report --trend`, git history mining) runs in seconds, far below client timeouts. Tasks' polling/durable-handle machinery is unjustified until a tool can exceed a single-request lifetime. Trigger to revisit: any tool (e.g. a future MCP-surfaced `init`/`adopt`, or a much larger repo under `report --trend`) that approaches client timeout. |
| Extensions framework | **NOTE (defer declaration)** | The framework is the right future home for declaring arggon-specific capabilities, but nothing we offer needs explicit negotiation today. Revisit when we add a capability a host must opt into. |
| MCP Apps | **DEFER (not applicable)** | We return JSON envelope text; there is no conversation-embedded UI need. The board viewer is a separate web surface. |
| Multi round-trip requests | **DEFER (not applicable)** | All tool input arrives in one call; interactive flows live in the CLI. |
| Cacheable list endpoints | **ADOPT (light, follow-up)** | Our `tools/list` is already static and deterministically ordered — ideal for prompt caching. Adding `ttlMs`/`cacheScope` hints is a small, forward-compatible follow-up; value is modest on stdio but cost is a few lines. |
| Authorization changes | **N/A** | stdio local transport, no HTTP endpoints, no tokens. Deprecations (Roots/Sampling/Logging) cost nothing — never implemented. |
| Official SDK migration | **DEFER** | The SDK's benefits (Web Standards, Workers, HTTP handlers, session plumbing) target transports we don't run. Our dependency-free server has full envelope control and test coverage. Revisit only if a second transport (HTTP/SSE) is added. |

Implementation lands via follow-up items (none opened by this research
task): (1) add `2026-07-28` to `SUPPORTED_PROTOCOL_VERSIONS` with tests;
(2) add cacheable-list hints to `tools/list` if the negotiated version is
≥ 2026-07-28.

## Consequences

- **Positive**: newer MCP clients can negotiate the current spec version
  without a rewrite; catalog caching hints arrive nearly free; a documented,
  honest position exists for each capability so future items don't re-litigate.
- **Negative / accepted risks**: the negotiated `2026-07-28` version is a
  compatibility claim on the core's *semantics* (stateless, tools), not a
  full reimplementation — clients expecting HTTP-native metadata
  (`Mcp-Method`/`Mcp-Name` headers) or `server/discover` are out of scope on
  stdio. If a future spec revision makes the new handshake mandatory on
  stdio, a real migration (likely on the official SDK) becomes necessary.
- **Neutral**: deprecations in the new spec touch nothing we ship.
