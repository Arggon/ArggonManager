# Exploration: Adopter upgrade experience (adopter-upgrade-experience-007)

Problem: when ArggonManager ships improvements (templates, methodology, new
commands), how do adopting repos receive them? Investigated 2026-09-16 in code
(`cli/src/init.ts`, `cli/src/docs.ts`, `cli/src/doctor.ts`, README
"Re-running init") and against the live adoption ArggonStores-am.

## Current mechanics (facts, not proposals)

- The tool itself updates by pulling the ArggonManager repo (root install,
  no package releases yet); `arggon --version` reads package.json (0.1.0
  since forever — the stamp exists but carries no information).
- Every generated doc records provenance in `tasks/.convention.yml`
  `x-generated:` →
  `{ template, checksum (sha256 of file as written), arggonVersion, generatedAt }`,
  plus an `acknowledged` flag from `arggon adopt --ack`.
- **Re-running `arggon init` is the designed upgrade path** (Copier-style):
  not-on-disk → created; untouched (checksum matches) → silently regenerated
  from the CURRENT template; adopter-modified → skipped by default
  (`--backup` = move aside + regenerate); **acknowledged → always skipped**
  ("it is yours").
- Doctor reports provenance buckets
  (`untouched/modified/acknowledged/acknowledgedDrifted/stale/missing`) but
  `stale` means "template no longer generated" (renames) — nothing reports "the
  upstream template content changed since you generated/acked".

### The structural finding (evidence)

ArggonStores-am (the reference adoption, 2026-09-15): **all 14 generated docs
are `acknowledged: true`** — the adoption flow sanctions every doc it
completes. Therefore re-running `init` there skips all 14: **the designed
upgrade channel is a no-op for every fully-adopted repo.** The 2026-09-16
methodology update (non-functional review bar + smoke gate) reached
ArggonStores-am only via a manual 7-step port. Ack semantics ("yours, never
touched again") and upgrade semantics ("untouched files get improvements")
are mutually exclusive, and every real adoption ends on the ack side.

## Options

### A. Visibility: `arggon init --dry-run` (plan mode; pure read)

No-write mode listing per destination what init WOULD do: created /
would-update (current template render differs from disk) / modified-skip /
acked-skip — with `--json` for agents. All the computation already exists in
`runInit`; only the write is gated. Effort: S.

### B. Staleness visibility: doctor `outdated` bucket

Doctor re-renders each managed destination's current template (placeholders
included) and compares with the on-disk file: render differs → the doc is
receiving nothing from a newer upstream. New informational bucket + counts,
pure read, runs on every `arggon doctor`. Effort: S-M (template rendering
must be side-effect-free and placeholder-stable).

### C. A safe upgrade flow for acked/modified docs (the core fix)

The ack must keep meaning "yours", while updates still arrive. Proposal:
`init --propose` (or `arggon docs propose-updates`) writes each new template
render to a side file (`<dest>.proposed-<arggonVersion>`) without touching
the acked/modified original; the adopting agent (or human) diffs and merges
as a normal work item, then `adopt --ack` re-acks the merged result. No
overwrites, agent-shaped, reuses the existing ack machinery. Heavier
alternative: git-based three-way merge (base = the file's first init commit
from the adopting repo's history; ours = current; theirs = new render) —
better UX for small diffs, more machinery and edge cases. Effort: M (propose)
/ L (three-way).

### D. Real version channel

Start bumping `package.json` + tagging releases so `arggonVersion` stamps
mean something; doctor then reports "docs generated by X, running Y". Enables
`whatsnew --since <v>` (structured changelog for agents) later. Without this,
"upgrade" is not even definable per repo. Effort: S (tags + bump discipline)
/ M (whatsnew command).

### E. Distribution upgrade (deferred)

Publish the CLI (npm package or GitHub release tarballs) so adopters update
the tool via a package manager instead of pulling this repo. Biggest change,
touches install docs and CI; needs its own ADR. Not required for A–D.

## Recommendation

Stage it: **B + A first** (make staleness and upgrade outcomes visible — pure
read, additive, no semantics change), then **C with the propose-file variant**
(safe channel for acked docs; three-way merge only if the proposal files prove
too manual), then **D** (version discipline so upgrades are tellable). E stays
deferred behind its own ADR. The pilot for the whole flow is ArggonStores-am:
after A–C land, its 14 acked docs should show `outdated` in doctor, receive
proposals via `init --propose`, and absorb the already-ported review-bar
update as the first merged proposal.
