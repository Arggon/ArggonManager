# CLI JSON output contract (schemaVersion 1)

Stable machine-readable stdout for agents and scripts. Every `--json` response is **exactly one JSON object** on stdout (plus a trailing newline).

`--json` is a **global** flag on the root program, also accepted after the subcommand:

```bash
arggon --json <command>
arggon <command> --json
```

Example: `arggon --json hello`.

The MCP server (`arggon mcp`) returns these same envelope objects as tool-result text content for its **fifteen** tools — `arggon_list`, `arggon_create`, `arggon_update`, `arggon_comment`, `arggon_handoff`, `arggon_show`, `arggon_next`, `arggon_report`, `arggon_validate`, `arggon_priority`, `arggon_sync`, `arggon_import_issues`, `arggon_start`, `arggon_branch` and `arggon_cleanup`, the registry in `cli/src/mcp-server.ts` (see [`ArggonManager/docs/agents.md`](./agents.md) §MCP server); kernel failures become tool errors carrying the same `ok: false` shape (see [`ArggonManager/docs/agents.md`](./agents.md) §MCP server). The native OpenCode V2 plugin tools (`tools.arggon.*`, W2/W3, the default path) return the identical envelopes in-process; a kernel failure is a typed tool error (`ArgonToolError`) whose message carries the code and the bounded `ok: false` envelope, and the session continues. When `arggon_comment`/`arggon_handoff` take their default `author`/`session` from `CallToolRequest.params._meta.sessionID`, the value is normalized before it reaches the envelope or the item body (task-opencode-v2-mcp-meta-hardening): a single-line token cut at the first whitespace, control, format or lone-surrogate character, capped at 64 characters with `…`, with a value that normalizes to empty treated as absent (see §MCP server in `docs/agents.md`). The tool input schemas are parity-tested against the CLI option surface (`cli/src/mcp-parity.test.ts`): the two surfaces stay in sync by test, not by convention — schema changes are **additive only**; a breaking change bumps `schemaVersion`.

Item-addressed MCP cwd (bug-mcp-server-binds-session-cwd-tracker-root): the item-addressed tools (`arggon_update`, `arggon_comment`, `arggon_handoff`, `arggon_show`) resolve their tree through the item's own `worktree_path` — the claim address `start --worktree` records — when the claim lives in another worktree, so their writes land on the item's branch instead of the server's launch tree. A write whose recorded claim tree is unavailable (gone, or no tracker there) is a tool error with `ok: false`, the calling command's `command` field, and `error.code: "TRACKER_ROOT_MISMATCH"` (the same named code the native surface uses); reads never refuse. Envelope shapes are otherwise unchanged — the `path` fields simply name the routed tree's copy. Behavioral for MCP callers, additive within `schemaVersion: 1`.

This flag is a formatter only. It does not walk the tracker tree or parse frontmatter. Commands that load domain objects pass those objects to the kernel operation that assembles the envelope (`lib/src/operations.ts`, exported by the kernel package entry `@arggondev/lib`); human vs JSON printing lives in the CLI entrypoint, so a machine surface never re-assembles an envelope on its own.

## Envelope

Every success or failure payload includes:

| Field               | Type    | Notes                                                                                                                                                                                                                                                                                                        |
| ------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ok`                | boolean | `true` on success; `false` on failure                                                                                                                                                                                                                                                                        |
| `schemaVersion`     | number  | JSON **output** contract version. Currently **`1`**. Not the task-tree convention version.                                                                                                                                                                                                                   |
| `conventionVersion` | number  | From the tracker `.convention.yml` (`ArggonManager/.convention.yml`, or legacy the tracker `.convention.yml`; `version`). Omit file = **`0`**.                                                                                                                                                               |
| `command`           | string  | Commander command name: `hello` \| `init` \| `doctor` \| `adopt` \| `list` \| `next` \| `report` \| `validate` \| `create` \| `update` \| `comment` \| `handoff` \| `branch` \| `start` \| `cleanup` \| `board` \| `sync` \| `import-issues` \| `instructions` \| `spec` \| `explore` \| `playbook` \| `mcp` |

Command-specific fields sit next to this envelope (not nested under a generic `data` key).

### Compatibility

- **Additive** fields are OK within a `schemaVersion`.
- **Breaking** changes bump `schemaVersion`.
- Clients **MUST ignore** unknown fields.
- This CLI emits **`schemaVersion: 1` only**.
- Distinct from the convention **tree** version in [`ArggonManager/docs/convention.md`](./convention.md). A v0 tree with JSON schema 1 is `{ schemaVersion: 1, conventionVersion: 0 }`; a v1 tree (with `branch`) reports `conventionVersion: 1`; a v2 tree (with `branch_patterns`) reports `conventionVersion: 2`; a v3 tree (with `milestone` + `depends_on` official) reports `conventionVersion: 3`; a v4 tree (priority field) reports `conventionVersion: 4`; a v5 tree (tracker root `ArggonManager/`) reports `conventionVersion: 5`.

### Failures (`ok: false`)

Include:

```ts
error: { message: string, code?: string }
```

Process exit code is **non-zero**. Do **not** mix human text onto stdout when `--json` is set; human diagnostics go to **stderr** only if needed (prefer a single JSON object on stdout).

Human failure lines are display-sanitized (bug-cli-error-output-injection, additive): the failure message can embed repo-controlled values (item file paths, config keys, git output), so the same policy as doctor human output applies — C0/DEL/C1/LS/PS escaped as inert text, and the raw message capped at `MAX_HUMAN_ERROR_CHARS` (2000, larger than the doctor report-value cap because error diagnostics are composite `<path>: <reason>` text). This is display only: the envelope's `error.message` always keeps the raw text, byte for byte.

Human success lines are display-sanitized too (task-success-stdout-sanitize, additive): dynamic values interpolated into success stdout — item ids/titles/paths and cascade lines from `create`/`update`/`next`/`comment`/`handoff`, branch names, `start` worktree/hook/PR values, GitHub issue titles from `import-issues`, and echoed argv paths such as `spec analyze --baseline`/`--save-baseline` — escape C0/DEL/C1/LS/PS as inert text and are capped at `MAX_HUMAN_ERROR_CHARS` (2000, the composite-diagnostic cap). Ordinary values render byte-identical except that `"` and `\` are JSON-escaped in place by the shared policy. `--json` payloads keep the raw values, byte for byte.

### Empty success

Empty success stays `ok: true` (e.g. future `list` with no items → `items: []`).

### Tracker-root binding (native surface only)

The CLI resolves the tracker root by walking up from its own `process.cwd()`, so
it has one candidate and never has to choose. The **native** `tools.arggon.*`
surface resolves per call from the calling session's directory, which means it
can hold two candidates against each other: the checkout it resolved into, and
the per-worktree identity the caller declares. That reconciliation is
native-only (full rule, sources and evidence: [`docs/opencode2.md`](./opencode2.md)
§Where every native tool resolves the tracker root).

Present **only when a worktree is involved** — a worktree identity was found at
the resolved checkout, or a declared worktree disagreed with it. A plain
checkout gets the CLI's bytes unchanged, which is what keeps the
native-mirrors-CLI byte-parity invariant (ADR 0011) holding. Additive within
`schemaVersion: 1`; no bump.

| Field                 | Type     | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `trackerRoot`         | `string` | The absolute **checkout** the tracker root resolved from (the tracker dir's parent — the same kind of thing a worktree identity names, so the two are comparable). Always present alongside `trackerWorktree` or `trackerRootMismatch`.                                                                                                                                                                                                                                                     |
| `trackerWorktree`     | `object` | The identity read from the resolved checkout's `.arggon.env` (spec [worktree-env-contract-016](specs/spec-worktree-env-contract-016.md)): `{ source, path?, id?, item?, branch?, stateDir?, cacheDir? }` in the documented key order. `source` is the `.arggon.env` path, or the literal `"process.env"` when the worktree session sourced that file. All of `ARGGON_WORKTREE_ID`, `ARGON_ITEM`, `ARGGON_WORKTREE_BRANCH`, `ARGGON_STATE_DIR` and `ARGGON_CACHE_DIR` are read and reported. |
| `trackerRootMismatch` | `object` | `{ resolved, declared[], sources[] }` — the checkout the call bound to, every worktree the caller declared, and where each declaration came from. On a **read** this is reported (reads are never refused); on a **write** it is refused instead, with `error.code: "TRACKER_ROOT_MISMATCH"`.                                                                                                                                                                                               |

No declaration anywhere (no `.arggon.env`, no sourced env) means no expectation,
so nothing is refused and none of these fields appear — the guard is narrow on
purpose so it cannot wedge correct work. Identity is compared by **path only**,
never by `ARGGON_WORKTREE_ID`: a long-lived host can carry a stale id from an
earlier worktree session while sitting at the right path. Reading the contract is
never fatal — a missing, unreadable, oversized or identity-free file declares
nothing.

#### The reaping family (`reaped[]` / `reapRefused[]`)

Selection never deletes — but a template that leaves a release does strand its destination, and under an auto-discovered seam directory (`.opencode/agents/`) a stranded file is still **dispatchable**. `init` closes that hole for the only destinations whose provenance it owns:

- an **orphan** is an `x-generated` destination whose recorded `template:` is absent from this arggon version — detectable with no new data, since the provenance already records it;
- `init` **removes** it only when every safety rule holds: inside the repo root, a regular file (never a directory or a symlink), recorded by no NEWER arggon than this one (a downgrade reports instead of deleting), and **byte-identical to the recorded checksum** (unchanged since the recorded baseline);
- anything else is **refused and named** in `reapRefused[]` with its reason — never-overwrite binds reaping exactly as it binds refresh;
- an **acknowledged** orphan (bytes unchanged) is the middle case: **refused by default, reaped only when the repo arms `x-tracker.reap-acked-orphans: true`**. `adopt --ack` acks every entry _and_ re-records its checksum from disk, so for an acknowledged entry a match proves only _unchanged since the ack_ — never _arggon wrote exactly these bytes_ — and provenance cannot separate "unedited" from "curated then acked". The refusal reason names the flag and the manual alternative; an armed reap still names the ack, so the audit trail shows a sanctioned file was removed deliberately. Bytes that DIFFER are refused regardless of arming. Full option in [`docs/convention.md`](./convention.md) §Tracker hygiene;
- the reaped destination loses its `x-generated` entry in the same run and the removal rides the auto-commit, so a later `init` reaps nothing (idempotent) and a committed tree never keeps provenance for a file that is gone;
- `doctor --agents` reports the same decision as the `orphaned` status (below) before anything is removed, so the migration is observable first.

Reaping is reported, never silent: `reaped[]` and `reapRefused[]` are top-level arrays (never folded into the `adapters.counts` create/replace/skip triple), `--json` carries both on every init run including `--dry-run` and `--propose` (empty there — a proposal sweep writes no file and deletes none), and human output prints one line per file, split by action so a removal can never read like a skip.

Bidi/zero-width format characters are deliberately not escaped — they cannot emit a control sequence or forge a line, and doctor output is a report, not an injection boundary. Resolution and posture: the matrix is read from the **examined tree only** — `<root>/adapters/capability-matrix.json`, the copy that tree carries, which `arggon init` generates on every scaffold (tier-1, provenance-tracked, never overwritten once adopter-edited) — with no fallback to the installed package. A tree that carries no matrix — never initialized, or initialized before `init` generated this destination — reports `present: false` with the reason in `error`, still exit 0. A copy that exists but does not parse is reported as an error rather than hidden, and the file is size-checked (`MAX_MATRIX_BYTES`, 16 KiB) **before** it is read. Human output adds one `matrix:` line plus one `gap: <invariant> x <agent> — <note>` line per gap row (capped, display-sanitized, notes are the actionable part — the full `mechanism` stays in `--json`), and both shapes say `report-only, never blocking`. The block is present on initialized **and** non-initialized reports (both probe the same tree root, the cwd when there is no tracker), and reports the absence with its reason rather than dropping the field.

### `list`

| Field        | Type         | Notes                                                                                                                                                                                                                                                                                                                           |
| ------------ | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `items`      | `WorkItem[]` | Lexicographic by `id`, per convention                                                                                                                                                                                                                                                                                           |
| `rankedFrom` | `object`     | Additive (bug-claim-pool-computed-from-main-misses-branch-claims): the checkout the items were read from — `{ branch, head, note }`. `branch` is the checked-out branch (`"HEAD"` when detached) and `head` the short HEAD sha, both `null` when git/the repository is unavailable; `note` is the bounded branch-claims caveat. |

Filters compose with the same engine as the flags. The v3 dependency predicates are `depends-on:<id>` (items whose `depends_on` contains `<id>`) and `blocked-by:<id>` (computed inverse — items that `<id>` waits for); `ancestor:<id>` matches items with `<id>` anywhere in their parent chain (the item itself does not count; unknown ids match nothing). All AND and negate (`!`) like the rest. `arggon list --parent <id>` is first-class sugar over the `parent:` predicate — exact direct-children match, ANDed with the flags and `--filter`; unlike the raw predicate, an unknown parent id fails with `LIST_FAILED` (`unknown parent "<id>"`) instead of matching nothing.

Stale-claim report: `arggon list --stale --older-than <duration>` (`<number><d|h|m>`, e.g. `7d`, `12h`, `30m`) limits the result to claimed items (in_progress + assignee) whose `claimed_at` is older than the threshold relative to now. It composes with the other filters; `--stale` requires `--older-than` (and vice versa) and invalid durations fail with `LIST_FAILED`. Claims from before `claimed_at` existed count as stale (advisory reporting only — staleness never blocks an update). A claim committed on an unmerged branch is **not in this tree** and therefore cannot be reported stale here — `arggon sync` reads the branch copies and reports it as a `branchClaim` (see `sync`).

Tree declaration (additive, bug-claim-pool-computed-from-main-misses-branch-claims): the items are the copies in ONE checkout — the one `rankedFrom` names. A claim made through `start` commits the item's frontmatter on the item's branch, so until that branch merges the primary checkout's copy still reads `todo`/unassigned. `list` (and `next`) never leave that boundary silent: every envelope carries `rankedFrom` with the branch-claims caveat, and the human output prints the same line. The surface that reconciles the branches is `arggon sync` (`branchClaims` / `branchClaimErrors`).

`Finding` is `{ file, kind, line?, severity, message }` — `file` posix, repo-relative; `severity` is `"info"` or `"warn"`; `line` (1-based, present when the finding is tied to a line) is reported against the full file including frontmatter. Kinds: `vague-quantifier`, `todo-marker`, `no-error-path`, `no-acceptance`, `untestable-acceptance` (ambiguity); `spec-orphaned`, `plan-spec-missing`, `duplicate-doc-number` (two documents sharing one number in `docs/adr/`, `docs/explorations/`, `docs/specs/` or `docs/plans/`; the same rule is a `DOC_NUMBER_COLLISION` warning in `spec validate`) (consistency); `DECISION-PENDING-EXPLORATION` (exploration whose Decision section records no ADR after 7 days), `STALE-PROPOSED-ADR` (ADR `- Status:` starting with `Proposed` with a `- Date:` older than 14 days), `SPEC-STATUS-DRIFT` (a `proposed` spec whose linked plan is `implemented`) (decisions — report-only, corpus mode only; baseline snapshots include them in the flat `findings` array); `MISSING-PRODUCT-ACCEPTANCE` (product acceptance — report-only, corpus mode only, and gated on arming, below); `UNANSWERED-DECISION-BRIEF` (decision brief — report-only, corpus mode only, and gated on the same arming, below).

**`findings.productAcceptance` — the product-acceptance detector.** A container of the convention's scope (`story`) that reached `done`/`cancelled` with no recorded `accepted` decision, per the `acceptance` classification documented under [`show`](#acceptance--the-product-acceptance-convention-not-the-done-gate). Its `file` is the **item's** path (not a document), so it has no `line`. It fires **only** when the project has armed the convention:

```yaml
# ArggonManager/.convention.yml
x-tracker:
  product-acceptance: true # opt in; absent or false = silent
```

Arming follows the `x-tracker.allow-steal` precedent (`ArggonManager/docs/convention.md` §Tracker hygiene): absent or `false` is silent, a non-boolean value is a `.convention.yml` parse error that `arggon validate` reports, and unknown nested keys stay ignored. A project with no product owner is therefore compliant by default and never sees a finding — absence of one is the point, not a defect. `self-accepted` and `changes-noted` both count as gaps (the question is whether the decision is on the record); a late `accept: approve` clears the finding on the next run, and nothing backfills historical items.

Report-only in every respect: findings never fail the run, no item is filed or mutated, no transition consults it, and `--spec <path>` (single-file mode) leaves the bucket empty like the others. A malformed `.convention.yml` degrades the detector to **unarmed** rather than failing the scan — `arggon validate` owns configuration errors. The bucket participates in `--baseline` like the others (a project that arms the convention will read these as NEW findings against a snapshot taken before arming).

**`findings.unansweredDecisionBrief` — the decision-brief detector.** An item carrying a `decide:` header with no later `decided:` comment, per the `decision_brief` classification documented under [`show`](#decision_brief--the-decision-brief-convention). Its `file` is the **item's** path (not a document), so it has no `line`. It inherits the **same** arming as the acceptance detector (`x-tracker.product-acceptance: true` — no new config key): a project with no product owner stays silent, and an unparseable `.convention.yml` reads as UNARMED rather than failing a report-only scan.

**Its scope is deliberately wider than the acceptance detector it mirrors.** `MISSING-PRODUCT-ACCEPTANCE` is scoped to terminal `story` containers because an acceptance is due _at closure_; a brief is owed while the decision is **open**, so this detector fires on **any item type and any status** — leaf or container, `todo`, `in_progress` or terminal — for as long as the item's state is `open`. Narrowing it by analogy would silence the one case it exists for: a brief sent and never answered, and nobody notices. `decided` and `self-decided` are both silent (the question was asked and answered), a late `decided:` clears the finding on the next run, and nothing backfills historical items.

Like the acceptance detector, it is **report-only in every respect**: findings never fail the run, no item is filed or mutated, no transition consults it, and `--spec <path>` leaves the bucket empty. Its message is deterministic — fixed enum tokens, no clock, no counts — so a committed `--baseline` fingerprints it stably.

Reopening is gated the same way (bug-reopen-ungated-cli, no config opt-in): `--status todo` on a `done`/`cancelled` item refuses non-TTY stdin with `--status todo on a done/cancelled item requires an interactive terminal (agents must not reopen — ArggonManager/docs/agents.md)`, and a declined TTY confirmation fails with `reopen aborted (confirmation declined)`. Both surface as `ok: false` envelopes with `code: "UPDATE_FAILED"`.

Done gate (task-done-gate-acceptance-waiver, ADR 0015; scoped by ADR 0025): `update --status done` on a `task`/`bug` whose LIVE `## Acceptance` section is not a complete acceptance contract refuses with `UPDATE_FAILED`, in one of two messages. **(a) An unticked criterion in that section** — checkbox lines with text after the box; a bare `- [ ]` is a scaffold placeholder, not a criterion (bug-empty-template-checkbox), so it is never in this set: `cannot mark '<id>' done: the acceptance checklist in the item's live '## Acceptance' section still has unchecked boxes. Tick every box there, or pass --waive "<reason>" to record a dated waiver`. **(b) No criterion published in that section at all** (the section absent, empty, or still the template placeholder — which is what `create` scaffolds): `cannot mark '<id>' done: the item's live '## Acceptance' section has no acceptance criteria (the section is absent, empty, or still the template placeholder — boxes inside dated '## Notes' comment blocks are history, not the contract). Record the real criteria in that section, or pass --waive "<reason>" to record a dated waiver`. The gate reads that section only, never the whole body: a dated comment block (`### <date> @<author>`, `### Waiver <date>`, through the next dated heading) is append-only history, so an unticked box in one never blocks the flip — which is what made the verdict depend on an item's comment record rather than on the work. A fenced code block is excluded on the same footing, and the fence is consulted before the heading rules: a `- [ ]` row inside a fence is never a criterion, a `## Acceptance` heading inside a fence opens no section, and a `### <date> @author` line inside a fence opens no comment block (an unclosed fence runs to the end of the body, per CommonMark). So a bug whose own repro demonstrates what a formatter does to a `- [ ]` list item is flippable, and a repro quoting `arggon comment` output cannot delete the live section below it; an item whose criteria exist only inside a fence refuses as (b), never as (a). `--waive "<reason>"` with a non-empty reason is the only way past EITHER refusal: it records a dated `### Waiver <date>` section in the item body BEFORE the flip (so the rationale travels with the item, visible in `show --body` and git history) and the flip proceeds like any other. Refusals, all `UPDATE_FAILED`: an empty/whitespace reason (`--waive requires a non-empty reason (the waiver is recorded in the item body)`), a waiver with nothing to waive — no `--status done` flip, a container type, or a satisfied live checklist (`--waive is only valid with --status done on a task/bug whose live '## Acceptance' section still has unchecked boxes or publishes no criteria (nothing to waive)`), and agent callers (`agents must not waive the done gate; --waive is a human-only escape hatch (ArggonManager/docs/agents.md §5)`) — the `arggon_update` MCP/native tool has NO waive property (documented parity exception in `cli/src/mcp-parity.test.ts`), so agents receive the plain refusal and coordinate with a human. Containers are not gated (their contract is the acceptance-aware cascade, which still asks the whole-body question); a satisfied live section flips as before; the transition table is never overridden (`blocked`/`todo` → `done` still fail the transition check first). The gate runs in the kernel, so every caller of `runUpdate`/`updateOperation` (CLI, MCP, native tools, `import-issues`' closed-issue flip) sees it; `import-issues` asks the same predicate before offering its waiver, and records the reason `imported as closed from GitHub issue #<n>` — so an imported body with no live contract (most GitHub issue bodies) waives it. Behavioral change, `schemaVersion` unchanged.

Tracker auto-commit (story-tracker-hygiene): `init` (bug-init-leaves-docs-untracked-start-blocks-on-clean-tree), `create`, `update`, `comment`, `adopt`, `cleanup --prune`, and `import-issues` commit ONLY their own mutated paths (`chore(tasks): <verb> <id>`; init uses `chore(tasks): generated init docs (N files)` for its bootstrap commit — generated docs, templates, the tracker tree and the tracker `.convention.yml` together — so a fresh init never leaves untracked tool-generated state that would block `start`'s clean-tree precondition); the user's pre-existing dirty files are never staged. Mutated paths a `.gitignore` rule matches are skipped (never force-added) and reported in the additive `ignored: string[]` array — one ignored path would otherwise abort `git add` after staging the rest, leaving a dirty index with no commit (bug-init-ignored-artifacts-dirty-commit). `--no-commit` opts out per invocation; the tracker `.convention.yml` `x-tracker.auto-commit: false` opts out tree-wide (flag wins over config, config wins over the default `true`). Skips are reported, never failures — the CLI works without git. Under git `index.lock` contention (bug-autocommit-silent-skip) the commit is retried with a short bounded backoff; if a skip is still unavoidable it is reported as `{ skipped: "git index locked" }` AND as a stderr warning (`commit skipped: git index locked`) — never silent. A "nothing to commit" result is a quiet benign skip ONLY when the mutated paths are genuinely clean (someone else committed the same content); if the paths still carry changes, a concurrent index rewrite lost this process's staged entry (task-nothing-to-commit-masking) and the skip is reported instead as `{ skipped: "nothing to commit (staged entry lost under contention)" }` plus a stderr warning — the mutation stays written-but-uncommitted for the caller to retry. Additive within `schemaVersion: 1`.

### `handoff`

With `--worktree` the claim commit, push, and draft PR run inside the worktree and the item's `worktree_path` is persisted (re-runs attach to the recorded path). Start prepares the worktree before the claim commit (the primary checkout's install is linked in as a per-worktree link farm when the worktree lacks one, and the workspace packages the worktree owns are built there before the gate) and never rolls the worktree back on failure: a failure after the worktree exists keeps the worktree and branch, and the failure message (human output and `error.message`) names the failing step, the kept path, a step-specific remediation and the fact that re-running `arggon start <id> --worktree` attaches to it (a failed push is the exception: attach does not retry it, and the message instructs `git push -u origin <branch>` manually) — the pre-commit gate is never bypassed (`--no-verify` is never passed). A workspace package the worktree carries its own copy of resolves to the **worktree copy** instead: start runs the package's own `build` script before the claim commit when that copy has no build output yet (printed on stdout), so the gate loads the branch's build; the build's exit is honored, so a failed build that still emitted the entry falls back visibly, and a build the install cannot consume (a bare symlink to the primary install has no farm to flip) is skipped; a copy that could not be built keeps the primary's copy and `linkedWorkspaces` names it — see the field's note above; the field is re-read after a `post-start` hook, so it matches the resolution the worktree is left with. A linked install mirrors the primary's, so a dependency declared since the primary's last install cannot be resolved from the worktree: `manifestCoverage` then reports `"stale"` and `missingDependencies` names what is missing (bug-worktree-readiness-misses-stale-primary-install) — informational, the start still lands the claim in a usable worktree, and the remedy is to re-install the primary checkout or give the worktree its own install. The project gate's binaries are checked the same way: `gateBins` names where each declared gate binary resolves from (`worktree`/`external`/`path`/`missing`), readiness is withheld while any of them resolves outside the worktree, and a claim-commit failure reports the observed resolution with the `npm ci` remedy instead of a bare `command not found` (bug-start-worktree-npm-ci-claim). With `x-tracker.strict-gate-bins: true` in the tracker `.convention.yml` that resolution stops being report-only (task-start-gate-strict-mode): `start --worktree` refuses the claim BEFORE the claim update — `claimCommitted: false` with `claimCommit.status: "not-attempted"` and `claimCommit.reason: "strict gate-bin gate refused"` — whenever the receipt reports any bin resolving `external`, `path`, or `missing` (the bin-resolves-nowhere flavor included), the failure message names each offending bin with its observed source plus the exact `npm ci` remediation and the attach re-run, and the worktree is kept for the fix. Unset or `false` keeps the default byte-identical on ATTACH runs: the same receipt is informational only and the claim commit stays authoritative. A start that CREATED the worktree is stricter by default, no flag required (bug-start-install-ordering): it must leave a gate-usable install, so the same violations refuse the claim BEFORE the claim update (`claimCommit.status: "not-attempted"`, `claimCommit.reason: "fresh-worktree install gate refused"`) with the offending bins, the `prepSteps` log that produced the state (its dropped-entry count included when the kernel's log cap shortened it — `stepsTruncated`/`stepsDropped`), the `npm ci` (or primary `npm install`) fix and the attach re-run; an attach re-run after the fix commits the claim. Default mode only lists. `--prune` removes removable worktrees (`git worktree remove` — git refuses dirty worktrees), deletes their merged branches (`git branch -d`), and clears the `worktree_path` records; skipped entries (non-terminal item, unmerged/missing branch, removal-blocking content) are never touched. Removal-blocking content is classified before anything is reaped (bug-cleanup-prune-untracked-artifacts-no-force), so the receipt never says `removable: true` and then fails on a raw git error: untracked blockers keep the conservative skip with `blockingPaths`/`blockingTotal` unless `--force` is passed (native `cleanup({ prune: true, force: true })`), which reaps that entry through `git worktree remove --force` and reports `forced: true`; tracked modifications are refused with or without the flag (`blockingTracked`/`blockingTrackedTotal` — the force opt-in never discards uncommitted tracked work); and the start-owned artifacts every run reaps itself (start's install link/farm, a start-shaped `.arggon.env`) are never blockers. `--force` requires `--prune`. Remote safety (bug-cleanup-partial-failure): when `origin/<branch>` exists, its tip must also be merged into `base` before anything is removed; otherwise the candidate is skipped with `reason: "remote branch divergent or behind (origin/<branch>) — push or delete the remote branch first"` (a lost final push must never strand the remote tip). Prune is transactional per candidate: all checks run before `git worktree remove`; if `git branch -d` still fails afterwards (race), the `worktree_path` record is cleared (the worktree is gone) and the leftover branch is reported via `leftoverBranch`. A recorded path that is no longer a live worktree — missing on disk, or a leftover directory whose gitdir link is gone (git lists the record as `prunable` after an interrupted `git worktree remove`, and then refuses the removal forever with "validation failed, cannot remove working tree") — is a stale record (bug-cleanup-stuck-when-worktree-dir-gone): the removal is skipped, the run drops the dead git record itself (`pruned stale git worktree record`; it pins the branch, so no manual `git worktree prune` is ever needed and `git branch -d` is no longer refused with "used by worktree"), the merged branch is still deleted and the `worktree_path` record is cleared; a leftover directory is left in place, never deleted by the reaper. Per-item prune failures never abort the run and do NOT raise `CLEANUP_FAILED` — they appear in `pruned` (`action: "failed"`, `error`) and `failures`. Exit-code contract (task-cleanup-json-exit-code): a partial prune still exits **0** with `ok: true` — `--json` consumers gate on the payload (`failures`, `pruned[].action === "failed"`), never on the process exit code; this deliberately diverges from the human path, which exits 1 when `failures` is non-empty (text output has no structured failure channel), and callers keying on exit status today see no change. A removal that did not observably happen is never reported as one: the native tool (which removes through the worktree domain) verifies the directory and `git worktree list`, falls back to `git worktree remove`, and on failure reports the leftover path and keeps the branch + record. Failures use `error.code: "CLEANUP_FAILED"` only for top-level errors (non-git tree, undetectable default branch). Declared Compose projects (task-cleanup-declared-services, ADR 0019 layer 2): when `.convention.yml` declares `x-worktree.services`, `--prune` tears down each removable worktree's per-worktree Compose project with `docker compose -p <project> down -v --remove-orphans` before `git worktree remove` (see [convention.md](convention.md) §Worktree bootstrap for the declaration grammar and [worktree-services.md](worktree-services.md) for the adopter pattern); with no declaration — or no docker CLI — cleanup never invokes Docker and reports `compose` (or nothing) instead. The native `cleanup` tool (OpenCode worktree domain) applies the same declaration, teardown, absent-docker degradation and bounded failure reporting ahead of its own removal, so its prune envelope matches `cleanup --prune --json` on the same fixture (task-native-cleanup-compose-parity). Squash merges (task-cleanup-squash-merge): when the ancestry check fails, cleanup queries gh (`gh pr list --state merged --head <branch> --json number,url,mergedAt --limit 5`); a merged PR makes the candidate prunable (branch deleted with `git branch -D`, actions annotated `via`), no match skips with `reason: "branch not merged and no merged PR found"`, and an unavailable gh skips with `reason: "ancestry check failed and gh is unavailable to check for squash-merged PRs"` — the gh lookup never breaks the run. `--no-gh` skips the fallback entirely (ancestry-only, for offline/CI use). `--release <id>` takes the other arm of the worktree domain (bug-unclaim-leaves-worktree-record-without-reaper): the inverse of `start --worktree` for a claim that was dropped. It classifies ONE item with the shared release rule (`classifyReleaseEntry`, the same one the native `cleanup({ release })` tool uses) and — on a releasable entry — reaps the declared Compose project, the start-created `.arggon.env`, the `arggon-claim.json` stamp and the worktree itself, deletes the branch (read from the WORKTREE, since the unclaim already cleared the recorded `branch`), then clears the `worktree_path` record; the branch delete is forced (`git branch -D`) because an abandoned branch is by definition not provably merged, and the worktree removal is forced only under `--take-over-worktree`. A recorded path that is not a LIVE worktree (missing on disk, a leftover directory whose gitdir link is gone, or the state after a manual `git worktree prune`) is a stale record for the release too (bug-cleanup-release-stale-record-wedge): the removal and the stamp/env steps are skipped while the declared Compose project is still reaped first — the project name derives from the recorded path, never from a live directory (task-release-stale-compose-reaping) — and a failed Compose reap aborts the release and keeps the record, so a retry can still reach the stack; the dead git record is pruned by the run itself (it pins the branch), the branch git's dead record still names is deleted and the `worktree_path` record is cleared — a leftover directory is left in place, never deleted. `--release` and `--prune` are mutually exclusive (two reapers, one run), and a release run does not survey: `candidates` is `[]`. Refusals keep the whole footprint intact (worktree, branch, stamp, record) and are reported on BOTH `released` (`action: "failed"`, `error` clamped like every sibling failure path) and `failures`, so the human path exits 1 while `--json` keeps exit 0 per the contract above. Three refusals: the item is still claimed (**unconditional** — `--take-over-worktree` never bypasses it), a stamp held by another identity whose window shows a live writer, and uncommitted/untracked content that blocks the removal (refused during classification, before anything is reaped, so the stamp and env file survive). `--take-over-worktree` is the audited hatch for a presumed-dead stamped owner on an unclaimed item, the only thing that forces the removal, and is refused without `--release` (`--take-over-worktree requires --release <id>`), mirroring `start`'s `--take-over-worktree` requiring `--worktree`.

#### `acceptance` — the product-acceptance convention (not the done gate)

`acceptance` is a **classification, never a gate**, and it is not the acceptance **checkbox** contract. Two different conventions share a word:

- **Product acceptance** (this field): the `accept: approve | accept: changes-requested` header line an operator writes as an ordinary `arggon comment` on a container. Prose on the item, never schema — there is no flag that writes it and no frontmatter field. States: `accepted` (the latest acceptance is an `approve`), `changes-noted` (it is a `changes-requested`), `none` (no acceptance comment), `self-accepted` (the latest `approve` was written by the item's own `assignee` — reported, never blocked; the tracker has no identity layer, so attribution is the only honest signal).
- **Acceptance checkboxes**: the `- [ ]` / `- [x]` rows the done gate reads (`acceptance_complete`, `acceptance[]` on the board drawer below). Unrelated grammar, unrelated rule; neither one reads the other. The checkbox contract is scoped to the item's live `## Acceptance` section (ADR 0025), so a `- [ ]` inside a dated comment block — or inside a fenced code block — is a row a renderer shows but never an obligation the gate counts.

Read from the item's canonical body, so the bounded comment tail cannot hide it — an acceptance filed as a comment (the default path, since `create` has no `--body` flag) is still classified. Carried on every view, `--meta` included. Reading the human (`arggon show`) view gains no field line: the acceptance is visible there as the item's own comment text, verbatim, exactly as before.

Classification is defined once in the kernel (`lib/src/acceptance.ts`, `classifyAcceptance`), and every surface reads it — the CLI, the MCP adapter and the native tools all consume this one envelope.

#### `decision_brief` — the decision-brief convention

`decision_brief` is a **classification, never a gate**, from the `decide:`/`decided:` header convention (ADR 0026, spec `owner-decision-brief-021`). The delivery lead asks a question with an ordinary `arggon comment` headed `decide: <the decision, free text>`; the product owner answers with a comment headed `decided: <the chosen option>` — or `decided: other` for "none of these", which is a first-class, unremarkable reply. Prose on the item, never schema — there is no flag that writes it and no frontmatter field. States: `none` (no `decide:` header), `open` (a brief with no later `decided:`), `decided` (a `decided:` follows the latest brief), `self-decided` (that answer was written by the item's own `assignee` — reported, never blocked; the tracker has no identity layer, so attribution is the only honest signal). **`self-decided` is a same-name hint, not an identity check:** an item assigned to the product owner's own login is legitimate, and the owner answering a brief on their own item reads `self-decided` — the normal owner answer, not an agent answering its own brief, because attribution cannot tell the two apart without an identity layer (ADR 0026, amendment of 2026-10-15). A later `decided:` supersedes an earlier one, and a superseded brief is never rewritten.

Read from the item's canonical body, so the bounded comment tail cannot hide it. The field is **ungated** — a pure read of the body, so all four states report whoever armed what; arming `x-tracker.product-acceptance: true` turns only the `spec analyze` detector on. Carried on every view, `--meta` included. The human (`arggon show`) view gains no field line — the brief is already visible there as the item's own comment text, verbatim, exactly as `acceptance` renders.

Classification is defined once in the kernel (`lib/src/brief.ts`, `classifyDecisionBrief`), and every surface reads it — the CLI, the MCP adapter and the native tools all consume this one envelope. Unlike `acceptance`, this state is **item-level, not a container aggregate**: `report --json` carries no `decision_brief` (a brief may live on a leaf, where `report` has no row), and `sync --json` is byte-identical.

It never gates: `report` still exits 0 with offenders listed, and `validate` is unchanged. The lists are bounded like the other kernel receipts (`MAX_HYGIENE_OFFENDERS` = 10, `MAX_HYGIENE_OPEN_CONTAINERS` = 5 per offender), with `offendersTotal` / `openContainersTotal` carrying the full counts so nothing is silently lost, and the human output names the same offenders with the same caps and overflow markers.

`--trend` mines git history (story-report-trend): a single `git log -p` pass over the tracker tree collects `+status:` frontmatter transitions per item file. Completions are first terminal transitions (`done`/`cancelled`) of ALL item types (initiative/epic/story/task/bug) bucketed by the ISO week of the commit's committer date, so story-driven projects get non-empty trends; cycle time is first `in_progress` claim → terminal in days, per leaf type (`task`/`bug`/`story` — containers stay excluded). Open items count as not-completed. `--since <YYYY-MM-DD>` (UTC) filters the considered window — transitions before it are ignored, so items completed before the window drop out entirely; an item whose claim predates the window completes without a measurable cycle time. `--since` requires `--trend`. Trend failures (non-git tree, `git log` errors) use `error.code: "TREND_FAILED"`; a tracker with no commits yet is not a failure and yields empty series.

Human output supports `--format table` (default) and `--format markdown` (standup summary: per-epic progress lines with `(done + cancelled)/total` completion, a Blocked section listing each leaf's `blocked_reason`, and a Hygiene section mirroring the `hygiene` payload). With `--trend` the trend block is appended to both (markdown gains a `## Trend` section). Markdown is stdout-only (not part of the JSON contract); both formats are pure tree reads — no network, no GitHub calls.

The served board always carries the **item detail drawer** (task-board-item-detail): cards become focusable (click/Enter) and open a read-only drawer fed by `GET /api/item?id=<id>`; the static export ships the same drawer only with the `--details` opt-in described below. That route is a pure kernel read (the bounded `show` path: prose + the last 3 comments) and answers `{ ok: true, item, detail }`: `item` is the contract WorkItem (including its repo-relative `path`), `detail` carries `prose`, `prose_truncated`, `acceptance[]` (`{text, checked, criterion}` rows parsed from the item's **canonical body** — see below), `acceptance_truncated`, `acceptance_complete`, `comments[]` (kernel tail; `{date, author, text, truncated}`), `hidden_comments`, `dependencies[]` (`{id, status, terminal}` — unknown ids get `status: null`, `terminal: false`, i.e. open, exactly like the card's blocked-by line), `parent` (`{id, status}` through the kernel's recorded `parent` edge, `null` when parentless; a dangling parent id gets `status: null`), `children[]` (`{id, status}` per item whose `parent` is this item's id, lexicographic id order), `open_descendants` (the server-side count of open descendants at every depth — `todo`/`in_progress`/`blocked` — that the tree row's `N open` badge and the derived `open` display read; `0` when the item has none; additive within `schemaVersion: 1`) and `pr` (the cached live-overlay match for the item's branch, or `null`). The payload is bounded by construction: prose is clipped at 8 KiB, each comment at 4 KiB of UTF-8, and the acceptance list at 64 rows, with `prose_truncated`/`comments[].truncated`/`acceptance_truncated` signalling each cut. The drawer renders the parent as a link that opens the parent's detail and lists each child as a link opening that child's detail (same fetch/snapshot path, focus stays trapped in the drawer); parentless/childless items render an honest `none`, and a dangling parent renders as text, never a link.

**Acceptance rows are read from the canonical body, not from the clipped prose** (bug-three-acceptance-parsers-diverging). `prose` is `show`'s bounded prose, which EXCLUDES comment sections, and it is byte-capped — so parsing rows out of it let the payload report "no unchecked criterion" on two shapes the done gate refuses: a checklist filed as a comment (`create` has no `--body` flag, so that is the default path for every new item) and a criterion beyond the 8 KiB cap. The rows therefore come from the whole item body through the kernel's one row parser (`acceptanceRows`, `lib/src/items.ts`) — the same parser and the same input as the gate that refuses `--status done`, which is why the drawer cannot contradict the gate. **The LIST and the VERDICT are then two different questions, on purpose** (ADR 0025): the list shows every row the item carries, history in dated comment blocks included, so a reader can see what was recorded; the verdict is `!acceptanceGate(acceptanceBody(item)).gated`, the gate's own answer over the item's LIVE `## Acceptance` section. So a row in `acceptance[]` can be unticked without `acceptance_complete` being `false` (a historical box), and `acceptance_complete` can be `false` on an item whose list is empty (no live contract published) — and the drawer still cannot contradict the gate, because the field that carries the verdict IS the gate's verdict. Three fields make that honest rather than silent:

| Field                      | Type      | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `acceptance[]` `criterion` | `boolean` | The row carries text, so it **gates** the done flip. A bare `- [ ]` is a row (it renders) but not a criterion (it does not gate) — the scaffold-placeholder rule. Additive within `schemaVersion: 1`.                                                                                                                                                                                                                                    |
| `acceptance_truncated`     | `boolean` | Rows beyond the 64-row cap were omitted from `acceptance[]`. Additive within `schemaVersion: 1`.                                                                                                                                                                                                                                                                                                                                         |
| `acceptance_complete`      | `boolean` | The DONE GATE's own verdict on the canonical body — `!acceptanceGate(...).gated`, so `false` means `--status done` is refused for either reason (an unticked criterion in the item's live `## Acceptance` section, or no criterion published there), whatever the row list shows. It rides beside the list precisely because the list is bounded — a clipped list must never read as "nothing left". Additive within `schemaVersion: 1`. |

**No `schemaVersion` bump.** All five are additive: no field removed, none retyped, none made optional, and every element of `acceptance[]` keeps `text` and `checked` with their existing meaning. The rule at the top of this document ("Additive fields are OK within a `schemaVersion`; breaking changes bump `schemaVersion`") covers this, and every prior field addition follows the same precedent. A consumer that validates the payload against a strict `additionalProperties: false` schema would need to relax it, which is the ordinary cost of an additive field and not a shape break. A blank id answers 400, an unknown id 404 with the kernel message, any other method falls through to the JSON 404, and the route never writes. The drawer renders every value as DOM text (`textContent` — bodies are untrusted markdown, never HTML), closes on Esc/close/backdrop with focus returned to the card, and closes when a live reload removes the item. The **plain static export deliberately embeds no item details**: without `--details` it stays byte-identical (no drawer markup, no endpoint wiring, no extra script), so an offline `board.html` carries item bodies only through the explicit opt-in above — with the documented per-item byte caps and the measured payload trade-off recorded there.

Moves that need a value collect it in an **in-page dialog** (task-board-move-dialogs, rendered on the static export too — the drop flow is the same in both): claiming into `in_progress` asks for the assignee, moving to `blocked` asks for the reason. The dialog validates inline (whitespace-only input keeps it open with a `role=alert` message), Esc/cancel/backdrop aborts the move with the drop-cancelled toast, focus is trapped in the panel and restored to the opener on close. A successful update offers an explicit `Undo` button in the toast when the REVERSE transition classifies as legal under the same embedded `evaluateDrop` parity rules (never force, never steal — undo re-enters `attemptMove`, so it collects a claim/reason through the same dialogs and reverts through the same `POST /api/update` path); a failed update keeps the existing revert path. The static export carries the dialog but its drops still fail against the missing endpoint and revert, exactly as before.

| `branchClaimErrors` | `object[]`                                                    | Branches whose item copy could not be read — `{ id, branch, pr, reason }`; claim state unknown, never assumed unclaimed                                                                                                                                                                                                                                                                                            |
| `exit_code`         | `0 \| 1`                                                      | Mirrors the process exit code                                                                                                                                                                                                                                                                                                                                                                                      |

Matching: items with a `branch` reconcile by exact head-ref equality (any type); empty `branch` fields are fill candidates only for leaves (`task`/`bug`) whose id starts a branch path segment and is not immediately followed by a letter or digit. Trailing hyphen suffixes deliberately still match — `feat/task-1-work` references `task-1` (this is what makes `chore/{id}-{type}` patterns fillable) — while `feat/task-12` does not reference `task-1`, and a longer id is never matched by its hyphen prefix (`feat/task-1` does not reference `task-1-work`). `--write` fills only empty fields — it never overwrites a set branch, never touches `status`, and never resolves ambiguity.

Verdict classification is additive within `schemaVersion: 1` and report-only: for every item the run reconciles with an open PR (matched / fillable / pending / ambiguous — never `no_pr` items), the item body's verdict comments (`verdict: approve | request-changes` header lines per `docs/engineering.md` §Review bar → Review verdicts) classify as `approved` (latest verdict is an approve), `changes-requested` (the latest verdict is a request-changes) or `none`. Classification reads item bodies already loaded by the run — no additional gh calls — and never affects matching or `exit_code`; a blocking merge gate is explicitly out of scope until the report proves low-noise.

Branch-resident claims (additive, bug-claim-pool-computed-from-main-misses-branch-claims). A claim made through `start` commits the item's frontmatter on the item's branch, so until that branch merges the primary checkout's copy of the item still reads `todo`/unassigned — `list`/`next` ranked from it cannot see the claim, and `start` refuses the re-claim from the branch/worktree copy (correctly). Sync reads the item file from the branch copies themselves for every locally-unclaimed claimable item: its recorded `branch`, every local (`refs/heads`) or fetched origin (`refs/remotes/origin`) ref whose name references the item id, and every open-PR head branch referencing it. Each `branchClaims` entry carries the claim found (`assignee`, `claimed_at`) and the `local` state it disagrees with; `branchClaimErrors` names branches that could not be read (not fetched, unreadable frontmatter), so an absent entry is never read as "unclaimed". Reads are local git only (`git show <ref>:<path>`) — no additional network beyond the PR list sync already fetches. Report-only: branch claims never gate matching or `exit_code`, exactly like `verdicts`.

A stale claim on a never-merged branch is reclaimable, but only through the human-only takeover gate: `sync` makes it visible (`branchClaims` carries `claimed_at`; `branchClaimErrors` says when the branch could not be read), and releasing or taking over the claim happens where it lives — the branch's worktree copy — via the interactive `update --steal --reason "..." --assignee <you>` (repo armed with `x-tracker.allow-steal: true`). Agents never steal. `list --stale` still cannot report a branch-resident claim: it reads one tree, and the claim is not in that tree.

**Exit-code semantics (differs from `ok`):** the process exits non-zero when check mode finds sync needed (`pending`/`ambiguous`) or the run errored, so `arggon sync --check` works as a CI gate after `arggon sync --write`. `ok` stays `true` for those — it is `false` only when the sync itself failed. Failures use `error.code: "SYNC_FAILED"` (missing a tracker, conflicting flags, or gh unavailable).

The example abridges `created[]` and `artifacts[]` (one row each, of 69). `artifacts[]` is emitted on every run; the sample shows the flagless **fresh-scaffold** default, where nothing is skipped and `counts.written` is every adapter destination. On an existing tree with a marker the same `mode: "detect"` reports `detected` and selects only those; with `--agents`/`--no-agents` the deselected seams carry `outcome: "skipped"` with the reason naming the agent and the selection label.

Init still **writes** the tracker `.convention.yml` (`ArggonManager/.convention.yml`, or legacy the tracker `.convention.yml`) (including the `x-generated` provenance section), `templates/`, and the governing docs (tier-1 by default; tier-2 with `--full`), then auto-commits exactly the files it wrote (tracker hygiene, bug-init-leaves-docs-untracked-start-blocks-on-clean-tree: a fresh init must leave a clean tree so `start`'s clean-tree precondition never blocks tool-generated state — non-git trees and git-absent machines skip the commit and init stays ok); `--json` only changes how the result is printed. Doc templates render `{{PROJECT_NAME}}` (target dir name) and `{{YEAR}}` at write time, and every generated file carries a `<!-- arggon:generated template="..." -->` marker as its first line. Re-run semantics are checksum-based (see [docs/convention.md](./convention.md) §Generated-doc provenance): entries flagged `acknowledged: true` (set by `adopt --ack`) are never regenerated — they land in `skipped[]` with their bytes untouched; untouched docs regenerate into `updated[]`, adopter-modified docs are skipped into `modified[]` + `skipped[]` (regenerated after `--backup`, with the old file archived to `backup/<YYYY-MM-DD>/<dest>` and listed in `backedUp[]`), so a second init on an untouched repo is `created: [], skipped: []` with every doc in `updated[]`.

### `adopt`

Agent-assisted adoption for existing repos (see [docs/agents.md](./agents.md) §Adoption sweep): inventories the governing docs and files the agent-executable migration task `task-adopt-arggon` under a parent story (`--story <story-id>`, else `story-arggon-adoption`, auto-created under the first epic). `--dry-run` computes the full payload and writes nothing — including the default story.

| Field                      | Type       | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `taskId`                   | `string`   | `task-adopt-arggon` — the created, planned (dry-run), or already-open task id                                                                                                                                                                                                                                                                                                                                                                                               |
| `storyId`                  | `string`   | Parent story id (`--story` override, `story-arggon-adoption`, or the existing task's parent on an idempotent skip)                                                                                                                                                                                                                                                                                                                                                          |
| `storyCreated`             | `boolean`  | `true` when this run created `story-arggon-adoption` (always `false` in dry-run and on skip)                                                                                                                                                                                                                                                                                                                                                                                |
| `createdContainers`        | `string[]` | Container ids auto-created this run when the tree had no epic (fresh `init --full`): `["arggon-adoption", "epic-arggon-adoption"]`; planned ids in dry-run; `[]` when an epic existed, `--story` was passed, or on skip (additive)                                                                                                                                                                                                                                          |
| `taskCreated`              | `boolean`  | `true` when this run created the task (always `false` in dry-run and on skip)                                                                                                                                                                                                                                                                                                                                                                                               |
| `skipped`                  | `boolean`  | `true` when an open (`todo`/`in_progress`) `task-adopt-arggon` already existed and creation was skipped (idempotent re-run)                                                                                                                                                                                                                                                                                                                                                 |
| `taskPath`                 | `string`   | Absolute path of the created or existing task file; `"(dry run — not created)"` in dry-run when nothing exists yet                                                                                                                                                                                                                                                                                                                                                          |
| `inventory`                | `object`   | Read-only doc inventory (below)                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `inventory.docs`           | `object[]` | One entry per scanned governing-doc path (standard destinations + common alternates), sorted by path                                                                                                                                                                                                                                                                                                                                                                        |
| `inventory.docs[].path`    | `string`   | Posix path relative to the repo root (e.g. `AGENTS.md`, `docs/convention.md`)                                                                                                                                                                                                                                                                                                                                                                                               |
| `inventory.docs[].exists`  | `boolean`  | Whether the file exists on disk                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `inventory.docs[].bytes`   | `number`   | File size on disk (`0` when absent)                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `inventory.docs[].managed` | `boolean`  | `true` when an `x-generated` provenance entry exists for the path — arggon-generated doc set (possibly edited since); an existing file without an entry is adopter-owned (content to extract)                                                                                                                                                                                                                                                                               |
| `inventory.stackHints`     | `string[]` | Stack manifests found at the repo root, filename only (`package.json`, `requirements.txt`, `go.mod`, `Cargo.toml`, `pom.xml`)                                                                                                                                                                                                                                                                                                                                               |
| `envGitignore`             | `object`   | Report-only probe of the tracked `.gitignore`'s `.arggon.env` entry (task-initadopt-report-only-arggonenv-gitignore-hint-for-adopters, spec worktree-env-contract-016, additive): the pre-flight doctor's own read, surfaced at the adoption moment — `{ path, present, ignores, hint }` with `hint` non-null exactly when the adopter's `.gitignore` exists and does not ignore `.arggon.env`; human output adds one `hint:` line. Nothing is written, modified or staged. |
| `dryRun`                   | `boolean`  | `true` with `--dry-run` (plan only, no writes)                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `commit`                   | `object`   | Tracker auto-commit outcome for the files written this run — ONE `{ hash, message }` commit covering the task and (when created) its story, or `{ skipped: <reason> }`. Additive within `schemaVersion: 1`; absent in dry-run / when nothing was written                                                                                                                                                                                                                    |

Failures use `error.code: "ADOPT_FAILED"` (not an arggon-managed tree — run `arggon init` first; no epic for the default story; `--story` that does not resolve to a story; or a terminal `task-adopt-arggon`, i.e. adoption already completed).

With `--ack`, the command takes a different, standalone payload (task-adopt-checksum-refresh): it acknowledges the CURRENT on-disk content of every generated doc (each path present in `x-generated`) as the new baseline — checksums are recomputed from disk and the state entries refreshed (`arggonVersion` + current timestamp) — so the sanctioned adoption-sweep edits stop reporting as modified. It writes only the tracker `.convention.yml`, creates nothing, ignores files absent from the state, and works even when `task-adopt-arggon` is already done. Each acked entry is additionally flagged `acknowledged: true`, so later `init` re-runs never regenerate it (the acked checksum is the adopter's content, not the template render — regenerating would destroy the sanctioned edits); hand edits made AFTER an ack stay protected the same way (the file lands in `skipped[]`, never `modified[]`-overwritten); `arggon doctor` surfaces them in the informational `docs.acknowledgedDrifted` bucket.

| Field   | Type       | Notes                                                                                              |
| ------- | ---------- | -------------------------------------------------------------------------------------------------- |
| `acked` | `object[]` | One entry per acknowledged doc, sorted by path: `{ path, checksum }` (the new `sha256:…` baseline) |
| `count` | `number`   | `acked.length`                                                                                     |

Failures with `--ack` also use `error.code: "ADOPT_FAILED"` (only the non-initialized-tree case — the ack needs the `x-generated` state init writes).
